# 交易复盘工作流

本工作流用于处理三类复盘任务：(1) TradingView 截图 + 单笔交易复盘；(2) 日内多笔机会扫描；(3) 跨日订单流 / CVD / 现货-永续分歧分析。共同目标是"数据驱动"，结论可追溯到 parquet 字段。项目仓库：`https://github.com/phoe8lin/tradereview`，本地路径 `/Volumes/external/trade/交易复盘/`。

## 三种模式

根据用户输入判断应走哪条路径：

| 用户提供 | 模式 | 编号规则 | 详细流程 |
|---|---|---|---|
| TV 截图 + 单笔交易（明确 entry/stop/take 和锚定 K 线） | **单笔模式** | 锚 K = `A0`，前负后正 | 见下文「单笔模式步骤」 |
| "帮我复盘今天" / 扫描日内多笔机会 / 无截图只说日期 | **日级模式** | 全日 `B00-B95`（15m），辅周期 `E00-EN` | 见文末「日级复盘流程」 |
| "看看 XX 多日 CVD / 资金费率 / 趋势分歧" / 跨日订单流分析 | **多日订单流模式** | 不需要 K 编号，直接日期+阶段命名 | 见文末「多日订单流分析流程」 |

产物落点：单笔/日级 → `reviews/<date>/`；多日订单流 → `reviews/<topic>/`。

---

## 全局原则（三种模式都适用）

1. **数据先行**：任何分析结论都必须能在对应 parquet 中找到字段支撑，**禁止凭直觉/截图肉眼估算**。
2. **统一时区 UTC+8**。`tools.validators.load_day` / `tools.daily_cvd_fetcher` 返回的 datetime 列**已经是 UTC+8 / UTC**，禁止再做时区偏移。
3. **默认交易所 Binance USDT-M 永续**（多日订单流模式默认同时拉现货）。其他交易所/现货只在用户明确指出时使用。
4. **Python 解释器**：统一 `/opt/anaconda3/envs/trade/bin/python`。
5. **代理**：依赖 `tools.config.PROXY`（127.0.0.1:7890），代理不稳定时等待节点切换后重试，**禁止**绕过代理直连。
6. **不凭印象写数字**：引用某根 K 的真实数值，必须从 `validators.get_bar(df, id)` / parquet 取（防止"wave 47.5→40.1 移花接木"）。

## 单笔模式核心原则

1. **锚 K 为 A0，前负后正**：`A0 = 用户截图中的"位置1 / 锚定 K 线"`；之前是 `A-1, A-2, ...`，之后是 `A1, A2, ...`。所有分析必须以编号引用 K 线，**禁止用自然语言描述位置**（如"左边那根""中间那根"），避免认错。
2. 全局原则全部适用（数据先行 / UTC+8 / 默认 Binance 永续）。

## 单笔模式步骤

### 步骤 1：从用户输入中提取关键信息

需要从截图 + 文字中确定：

- 标的（`base/quote`，如 BTC/USDT）
- 周期（如 5m / 1h）
- 交易所（默认 binance，永续/现货）
- **锚定 K 线时间**（UTC+8 的精确时间，**必须精确到分钟**）
- 方向（long / short）
- 入场价 / 止损价 / 止盈价

**如果锚定时间不精确，必须先向用户确认**，不要猜。价格数据不对会导致后续所有分析失效。

### 步骤 1.5：保存截图到 raw/ 目录（可选但强烈建议）

**Cascade 无法代你保存图片**，需要你自己操作：

1. 在本地把 TV 截图另存为 `reviews/<date>/raw/<trade_id>.png`（或 .jpg/.jpeg/.webp）
   - 例：`reviews/2026-04-19/raw/HYPE_5m_001.png`
2. `review_builder` 会自动检测该文件并在 `review.md` 中嵌入 Markdown 图片引用
3. 之后在 IDE 或 GitHub 里打开 `review.md` 就能直接看到截图

如果步骤 1 跳过，review.md 就没有截图区（其他内容不受影响）。

### 步骤 2：生成复盘包

```bash
# 在项目根目录执行
/opt/anaconda3/envs/trade/bin/python -m tools.review_builder \
  --date YYYY-MM-DD \
  --trade-id <标的>_<周期>_<序号> \
  --base <BASE> --quote USDT \
  --timeframe <周期> \
  --anchor "YYYY-MM-DD HH:MM" \
  --entry <价> --stop <价> --take <价> \
  --direction <long|short> \
  --notes "<一句话概述>"
```

产物：
- `reviews/<date>/data/<trade_id>.parquet` — 带指标和特征的完整 K 线
- `reviews/<date>/replicated/<trade_id>.html` — Plotly 交互图（4 行布局：K + Wave + Delta/CVD + Volume Profile；Delta/CVD 仅在存在 `<trade_id>.orderflow.parquet` 时启用；VP 始终启用，含 POC/VAH/VAL 叠加、micro-VP footprint、可折叠概念速查面板）
- `reviews/<date>/trades/<trade_id>.yaml` — 结构化元数据
- `reviews/<date>/review.md` — 当日复盘累计文档（自动 append 一段）

**若需 Delta/CVD 子图**：先单独跑 `tools.orderflow_fetcher` 拉 `.trades.parquet` + `.orderflow.parquet`，再跑 `review_builder` 自动接入。命令见 `@/Volumes/external/trade/交易复盘/README.md` 的"订单流（按需启用）"段。

### 步骤 3：数据核验（防认错）

生成后**立即**用 pandas 读 parquet 打印锚 K 前后 10 根数据，核对：

- 锚 K 的 OHLC 是否与截图显示的 hover 值一致（误差 < 0.1%）
- 如果不一致 → 锚定时间错了，回步骤 1 重新确认

```bash
/opt/anaconda3/envs/trade/bin/python -m tools.calibration.stochrsi_check \
  --data reviews/<date>/data/<trade_id>.parquet --window 10
```

### 步骤 4：分析

**引用规则**：
- 所有 K 线引用使用编号（A-3, A0, A5 等），**且必须附带时间点**避免用户在 TV 图上多标记时搞混
  - 同日内：`A0 (14:50)`、`A-2 (14:40)`
  - 跨日：`A0 (04-20 14:50)`
  - 表格中若已有"时间"列可省略 inline 时间，正文引用必须补
- 每个结论后括号注明依据字段，如"A0 (14:50) Wave 46.86 严重超买" 而不是"A0 超买"
- K 线形态特征字段要点：
  - `upper_wick_ratio` = 上影比例，`lower_wick_ratio` = 下影比例（**注意别搞反**）
  - `body_ratio` = 实体比例
  - `vol_vs_ma` = 成交量/20根均量，>1.5 视为放量
  - `engulf` ∈ {`bull`, `bear`, ``} = 吞没形态
  - `wave` ∈ [-50, 50]，>+40 超买，<-40 超卖

### 步骤 5：用户交互讨论

让用户指认位置2/位置3 等关键 K 线的编号后再展开分析，不要自己猜。

### 步骤 6：落实结论到 review.md

分析完成后追加到 `reviews/<date>/review.md`：
- 关键 K 线映射表（位置 ↔ 编号 ↔ 时间 ↔ 关键数据）
- 本单结论（3-5 条）
- **心得标签**（`#xxx #yyy` 格式，方便日后跨复盘检索）

## 单笔/日级常见错误与防御

> 适用单笔模式 + 日级模式。多日订单流模式的常见误用见「多日订单流分析流程」步骤 M0。

| 错误 | 防御 |
|---|---|
| 看反 `upper/lower_wick_ratio` | 分析前先在脑海中复述字段含义 |
| 锚时间猜错导致价格区间不匹配 | 单笔步骤 3 / 日级步骤 D3 强制核验 |
| 用自然语言"左边那根"误指 | 单笔用 A 编号，日级用 B/E 编号 |
| 指标读数凭印象 | 每个数字都从 parquet 取 |
| 时区误加 8h（datetime 已是 UTC+8）| 必须用 `tools.validators.load_day` 取数 |
| ad-hoc 订单流脚本用 naive `datetime(...).timestamp()` 做 5min 分桶 → 在不同系统 TZ 下 bucket 偏移，早期 trade 被塞到"未来桶" | **优先用 `tools.orderflow_fetcher`**（`(timestamp_ms // tf_ms) * tf_ms`，时区无关）；确需写一次性脚本时，分桶**必须**用 `pd.Timestamp(..., tz="Asia/Shanghai")` 与 `pd.to_datetime(..., utc=True).dt.tz_convert("Asia/Shanghai")`，**禁止** `datetime(y,m,d).timestamp()` + 手动 `+28800` 这种 naive 路径 |
| "ema 被拒"但价格没触及 | 用 `validators.ema_relation(bar)` 输出结构化 state |
| entry 价不在 K 线区间或 RR 不自洽 | 写入 review.md 前必须跑 `tools.validators.run_review`（日级步骤 D3.5；单笔模式如有疑问也建议跑）|
| wave/delta 数据张冠李戴 | 用 `validators.get_bar(df, id)` 取，禁止凭记忆 |
| "今天是 bear 趋势日"忽略时段 | 用 `regime_summary(df)`，dominant_pct < 60% 即按震荡日处理 |
| "absorption" 概念误用（同向放量也叫 absorption）| 用 `detect_features(bar)`，只有阳/阴线方向 vs delta 方向**相反**才算 |
| "长上影"凭眼观感 | 用 `detect_features(bar).patterns`，阈值 upper_wick_ratio ≥ 0.4 |
| 趋势线+Wave+Delta 共振就认为可以入场 | **共振 ≠ 触发信号**。趋势线/Wave 极值/Delta 衰竭是"观察条件"，不是"入场条件"。入场必须有一根**触发 K 线形态**（bear engulf / 长上影拒绝 / absorption / 放量反转实体），否则就是赌。事后看逻辑完美的机会，事前往往缺这根触发 K——诚实承认"抓不到"比强行找入场点更有价值 |
| 把 delta 正负交替当成"趋势已形成" | 用**两级框架**判断：**Level 1（定方向）**= EMA200 方向 + regime，决定倾向多还是空；**Level 2（找入场）**= Wave + 前高前低 + CVD + 吞没等，决定具体入场时机。Level 2 的局部矛盾（如 delta 偏态未转）不推翻 Level 1 的大方向。Level 2 与 Level 1 同向→趋势延续逻辑，可拿久；反向→均值回归逻辑，吃短段就走，别幻想反转 |

## 5m/15m/1h Delta/CVD 数据源策略（单笔/日级共用）

**核心原则**：bar-level delta/cvd **永远来自 klines.taker_buy_base**（便宜、零分页 bug、零时区错位），仅"形态可疑"的 K 才拉 aggTrades 留微观证据。

### 三种模式

| 模式 | 行为 | 用途 |
|---|---|---|
| `klines` | 仅 klines，全窗口 bar-level delta/cvd | 最快；普通 5m/15m/1h Delta/CVD 子图够用 |
| **`hybrid`（默认）** | klines 全窗口 + 命中钩子的 bar 自动拉 aggTrades | 默认场景；保留关键 bar 的 footprint 微观证据 |
| `full` | 整窗口 aggTrades（旧行为） | 大范围微观分析（极少用） |

### 钩子（命中即把该 bar 加入"热点集合"，再加 buffer，合并连续段一次性拉 aggTrades）

| 钩子名 | 触发条件 | 默认 |
|---|---|---|
| `anchor` | 锚 K（A0） | ✅ |
| `long_upper_wick` | `upper_wick_ratio ≥ 0.4` | ✅ |
| `long_lower_wick` | `lower_wick_ratio ≥ 0.4` | ✅ |
| `absorption_candidate` | 阳线+Δ负 / 阴线+Δ正，且 \|Δ\|/vol ≥ 0.05 | ✅ |
| `engulf` | bull/bear engulf | ✅ |
| `wave_extreme` | \|wave\| ≥ 40 | ✅ |
| `high_volume` | `vol_vs_ma ≥ 1.5` | ❌ |

阈值 / 默认钩子 / buffer 见 `@/Volumes/external/trade/交易复盘/config/defaults.yaml:55`，**不要在调用处硬编码**。

### 调用方式

```bash
# 默认 hybrid + 默认钩子（推荐，模型一行就够）
/opt/anaconda3/envs/trade/bin/python -m tools.orderflow_fetcher \
  --date <YYYY-MM-DD> --trade-id <id>

# 仅 klines（用户明说不要 footprint，最快）
... --mode klines

# 整窗口 aggTrades（旧行为，慎用）
... --mode full

# 显式钩子 / buffer（临时覆盖配置）
... --hooks anchor,long_upper_wick,absorption_candidate --buffer-bars 2

# 强制纳入特定 bar（无视钩子）
... --extra-bar-ids A0,A-1,A2
```

### 产物

- `<id>.orderflow.parquet` — 全窗口 K 线 + delta/cvd（永远来自 klines）
- `<id>.trades.parquet` — aggTrades 原始数据（hybrid: 仅热点段；full: 整窗口；klines 模式不写）
- `<id>.hotspots.json` — 命中记录（hybrid/full 写）：`hooks_used / buffer_bars / hotspots[bar_id, matched] / ranges / agg_trades_coverage_pct`

### 模型决策铁律（防止选错模式）

1. **默认就用 hybrid**——模型 99% 情况下不需要决定模式，跑默认命令就好
2. **想最快、确定不需要 footprint VP** → 显式 `--mode klines`
3. **整段窗口的微观分析（如手工 footprint 全量）** → 显式 `--mode full`
4. **klines 推的 delta 与 aggTrades 聚合的 delta 在 bar 边界有 0~8% 差**（aggTrades 翻页 epsilon 导致），**以 klines 为准**——这是 v2 NEAR 案例确认的事实
5. **report 里要引用 hotspots.json** 说明哪些 bar 有 footprint 数据可用、哪些只有 bar-level delta

### 与 review_builder 的协作

`review_builder` 不变；下游 `multi_trade_chart` / Plotly 报告读 `<id>.orderflow.parquet` 渲染 Delta/CVD 子图，读 `<id>.trades.parquet`（如存在）渲染 footprint VP——没有 trades.parquet（klines 模式）时自动降级为 OHLCV 近似 VP。

## 日级复盘流程

**触发条件**：用户没给截图，也没给具体交易参数，而是说"复盘一下今天 XX"、"扫一下今天 HYPE 15m"、"今天有哪些机会"、"我想看看今天整天"——走日级模式。

### 步骤 D1：确认基本要素

只需要和用户确认：
- **日期**（UTC+8，默认"今天"）
- **标的**（如 HYPE/USDT）
- **主周期**（默认 15m，可改 5m/1h）
- **辅周期窗口**（可选，如某段时间想看 5m 细节）
- **交易所**（默认 binance futures）

### 步骤 D2：一键生成数据 + 骨架

```bash
/opt/anaconda3/envs/trade/bin/python -m tools.day_review_builder \
  --date YYYY-MM-DD --base <BASE> --timeframe 15m \
  [--supp-tf 5m --supp-window "HH:MM-HH:MM"]
```

产物：
- `reviews/<date>/data/day_<BASE>_<TF>.{parquet,txt}` — 主周期全日 + EMA + Wave + 形态 + 订单流，编号 `B00-B95`
- `reviews/<date>/data/supp_<BASE>_<SUPP_TF>.{parquet,txt}` — 辅周期窗口，编号 `E00-EN`（可选）
- `reviews/<date>/review.skeleton.md` — 每次刷新的骨架，含自动识别的长影/放量/吞没/EMA100 触点/Wave 峰谷
- `reviews/<date>/review.md` — **首次创建复制骨架；已存在不覆盖**

**增量更新**：同一日可多次运行，parquet/skeleton 都会刷新，review.md 的手写内容受保护。

### 步骤 D3：读表、识别、讨论

1. 读 `data/day_<BASE>_<TF>.txt` 掌握全日走势
2. **先跑 EMA regime 切片**（防止"今天是 bear 趋势日"的笼统判定）：

   ```python
   from tools.validators import load_day, regime_summary, regime_segments
   df = load_day(date, symbol, tf)
   print(regime_summary(df))      # 主导 stack / 是否趋势日 / 切换次数
   print(regime_segments(df))     # 每段时间区间
   ```

   把全日切成 `bull_stack / bear_stack / tangled` 时段——**任何"全天趋势"判断必须基于 dominant_pct ≥ 60%**，否则按"震荡/混合日"处理，分时段分析。

3. 参考 `review.skeleton.md` 自动识别列表 + `bar_features.detect_features` 验证候选 K 线形态：

   ```python
   from tools.validators import detect_features, scan_features
   detect_features(get_bar(df, "B193"))   # 单根：返回 patterns + evidence
   scan_features(df, "B190:B225", patterns=["bull_absorption","bear_absorption"])
   ```

   `absorption` 特别注意：**阳线 + 负 delta = bull_absorption（吸筹）**，**阴线 + 正 delta = bear_absorption（吸卖盘）**——同向放量大阴/大阳是普通推动，**不是 absorption**。
4. 逐个与用户讨论（**先 Level 1 后 Level 2**）：
   - **Level 1**：EMA200 方向？regime 是什么？整体偏多还是偏空？
   - **Level 2**：你看到了什么结构（前高前低/Wave/CVD/吞没）？
   - Level 2 与 Level 1 同向还是反向？→ 决定持仓预期（趋势延续 vs 均值回归）
   - 你看到了什么结构？
   - 该位置是否符合你的交易系统（趋势/形态/量能/wave）？
   - 入场/止损/止盈分别放哪？R:R 够不够？
   - 信号强度 A+/A/B/C 自评，对应仓位 1R/1R/0.5R/跳过
5. 后验验证：用 parquet 数据确认止损是否触发、止盈是否达成、持仓时长、实际 delta 印证

### 步骤 D3.5：参数与信号自动校验（强制，P1+P2 工具）

**任何写进 review.md 的"入场/止损/止盈"参数，必须先过 `tools.validators` 校验**，否则不得落笔。

#### D3.5.1 创建/更新 `reviews/<date>/trades_validate.yaml`

把当日所有候选/实际入场点写进 yaml（参考 `reviews/2026-04-26/trades_validate.yaml`）：

```yaml
date: YYYY-MM-DD
symbol: HYPE
timeframe: 5m
trades:
  - id: B193                              # 入场 K 编号
    side: short                           # short / long
    entry: 41.242                         # 必须 ∈ OHLC，否则视为限价单
    stop: 41.336
    take: 41.112
    rr: 1.38                              # 可选，会被 D 项一致性校验
    template: short_reversal_overbought   # 可选；填了就跑 5 要素打分
    anchor: B192                          # template 不为空时必填
    notes: "首仓 / 加仓 / 一句话备注"
```

#### D3.5.2 一键生成校验报告

```bash
/opt/anaconda3/envs/trade/bin/python -m tools.validators.run_review \
  reviews/<date>/trades_validate.yaml \
  > reviews/<date>/auto_validation.md
```

产物：`reviews/<date>/auto_validation.md`，含汇总表 + 逐笔详情（A-G 七项校验 + 5 要素打分）。

#### D3.5.3 红灯处理铁律

| auto_validation 标记 | 处理方式 |
|---|---|
| **OVERALL = FAIL** | review.md 写"不该做"或"参数无效"，禁止把它当作有效信号收录 |
| **OVERALL = WARN** | review.md 必须用一句话明确警告原因（如"擦边兑现 / 止损跨越 ema_200"） |
| **signal score < 3/5** | 即使后验命中，也判定为"运气兑现"而非有效模板 |
| **B_reachability = FAIL** | 限价单不可达 → entry 数字必须更正 |
| **A_entry_in_ohlc = FAIL** | entry 不在 K 线区间 → 数字写错 |
| **D_rr_math = FAIL** | claimed RR 与三件套不自洽 → 三选一改正 |

#### D3.5.4 数据时区与编号

`tools.validators.load_day` 已固化两条铁律，所有分析用它取数：
- parquet `datetime` 列**已是 UTC+8**，禁止再做时区偏移
- K 线编号 `B{n}`（不补零、两位补零、三位补零均接受）

如需在文档中引用某根 K 的真实数值，必须从 `validators.get_bar(df, "B193")` 取，**禁止凭印象写**（防止类似"wave 47.5→40.1 移花接木"的错误）。

## 多笔合并绘图（单笔/日级可选）

**触发条件**：同一日同标的同周期，**多笔交易时间相近**（如同日内 3 笔 5m 多单），想在一张图里对比入场/止损/止盈 → 使用 `multi_trade_chart`。仅适用单笔/日级模式（多日订单流模式不需要绘图）。

**前置**：每笔 trade 必须先由 `review_builder` 生成，以便拿到 `trades/<trade_id>.yaml`。

```bash
/opt/anaconda3/envs/trade/bin/python -m tools.multi_trade_chart \
  --date YYYY-MM-DD \
  --trade-ids ID1,ID2,ID3 \
  --output <输出文件名（不含.html）> \
  [--with-cvd] \
  [--no-vp] \
  [--padding-bars 10]
```

特点：
- **自动复用 `day_<BASE>_<TF>.parquet`**（若已由 `day_review_builder` 生成），无需重复拉取。
- `--with-cvd`：在 CVD 子图绘制 CVD，按需抓取（优先复用 day parquet 中的 cvd 列；否则对每个 trade 调一次 `orderflow_fetcher`）。**不需要 CVD 就不加这个开关，不浪费网络**。
- **Volume Profile 默认启用**：合并各 trade 的 `<id>.trades.parquet`（有则用 trades 精确版，否则用 show 窗口 OHLCV 近似）画 POC/VAH/VAL 主图叠加 + 右侧大 VP 子图 + 可折叠概念面板。`--no-vp` 关闭。
- 每笔 trade 用独立颜色（①②③④⑤），entry/stop/take 仅从 anchor 向右延伸，不贯穿全图。
- 一致性校验：trade_ids 必须共享 exchange/market/symbol/timeframe，否则报错。

产物：`reviews/<date>/replicated/<output>.html`

**使用时机判断**：
- 3 笔以内 + 时间跨度 ≤ 1 天 → 合并一张
- 不同标的 / 不同周期 → 分开画（工具会拒绝）
- 1 笔 → 用 `review_builder` 本身即可，不需要合并

## 多日订单流分析流程

**触发条件**：用户提到"看看 XX 这段时间 CVD"、"为什么价格涨/跌但 CVD 反向"、"现货 vs 永续分歧"、"多日趋势分析"——走多日订单流模式。**典型反例**：单笔/日级模式下 K 编号引用是核心，多日模式不需要 K 编号，关注的是日级聚合 + 阶段切分。

### 步骤 M0：核心铁律（**写之前先背一遍**）

> 这一节是从 `reviews/near_cvd_analysis/` 翻车案例里沉淀出来的，**违反任意一条结论都不可信**。全局原则（UTC+8 / 数据先行 / 不凭印象写数字）默认包含在内。

1. **数据源铁律**：日级 CVD 一律用 Binance klines 自带的 `taker_buy_base_asset_volume` 推算（`delta = 2 × taker_buy_base − volume`）。**禁止**用 aggTrades 的 `fromId` 翻页做日级累计——跨日 ID 不连续会丢段，多日采样下 4 天里有 2 天方向反掉的事实案例已记录。
2. **双端必拉**：永续 + 现货 OHLCV，**缺一不可下结论**。Binance 上多数币现货占总成交 30%+，只看永续 CVD 等于看半张图。
3. **必拉 funding rate**：任何永续 CVD 趋势判断**必须先看 funding 方向**。`perp Δ 负 + funding 正` ≠ 卖方主导，可能只是空头被绞肉机的机械结果。
4. **数据核验**：如果**确实**用了 aggTrades（如分钟级 footprint），必须跑 `cross_check`：klines 的 `volume.sum()` vs aggTrades 的 `qty.sum()` 偏差 >5% 立即排查。
5. **强制证伪**：写结论前必须先列出"如果我错了，应该看到什么"，把这些反向证据也拉出来对照。**未经证伪的叙事不算结论**。
6. **分阶段不能整段平均**：>30 天的阶段必须按月或周细分；80 天的阶段如果中间某月行情反转，整段平均会把转折掩盖掉。
7. **常见误用清单**（直接拒绝）：
   - `absorption` 必须**单日**判定（阴线 + 正Δ 或 阳线 + 负Δ），**禁止**扩展到一整段时间称为"持续吸筹"
   - "perp Δ 负" ≠ "卖方主导"——必须先用 funding 方向排除"空头被挤"情形
   - top trader 多空账户比 > 2 视为**反向预警**（散户极度看多），不视为多头确认
   - "持续吸筹"叙事如果只在永续端成立、现货端反向，立即作废
   - "CVD 跌价格涨" 在永续端是常见现象（funding 正 + 空头强平），**默认归因不是 absorption**

### 步骤 M1：拉数据（一条命令）

```bash
/opt/anaconda3/envs/trade/bin/python -m tools.daily_cvd_fetcher \
  --base <BASE> --start <YYYY-MM-DD> [--end YYYY-MM-DD] \
  --markets perp,spot --funding --oi --lsr \
  --out-dir reviews/<topic>/data
```

产物（同时存 parquet + csv）：

- `<base>_usdt_perp_daily.{parquet,csv}` — 永续每日 OHLCV + delta + buy_ratio + cvd
- `<base>_usdt_spot_daily.{parquet,csv}` — 现货同上
- `<base>_usdt_funding.{parquet,csv}` — funding rate 全历史（8h 一次）
- `<base>_usdt_oi_1d.{parquet,csv}` — OI 历史（仅近 30 天）
- `<base>_usdt_top_lsr.{parquet,csv}` — top trader 多空账户比（仅近 30 天）

CLI 末尾会打印 summary（每端起止价/累计 Δ/buy%、funding 累计成本、OI 起止、LSR 区间），先用这个粗看再决定深挖方向。

### 步骤 M3：分阶段聚合（按月最稳）

不要笼统聚合超过 30 天的阶段。最小可接受粒度：

```python
df["mon"] = df["date_utc"].str[:7]
agg = df.groupby("mon").agg(
    days=("date_utc", "count"),
    px_first=("open", "first"),
    px_last=("close", "last"),
    delta=("delta", "sum"),
    vol=("volume", "sum"),
    buy_w=("taker_buy_base", "sum"),
)
agg["chg%"] = (agg["px_last"]/agg["px_first"]-1)*100
agg["buy%"] = agg["buy_w"]/agg["vol"]*100
```

阶段定义除"按月"外，可按 EMA200 方向 / 价格区间突破划。**禁止**把 70+ 天的"震荡偏上行"段当一整块，必须切成至少 2-3 段。

### 步骤 M4：双端 + funding 联立解读模板

| 永续 Δ | 现货 Δ | funding 方向 | 解读 |
|---|---|---|---|
| − | + | + | **现货带涨 + 永续空头被挤**（v2 NEAR 案例） |
| + | + | + | 双端追多，趋势确认（注意过热） |
| − | − | − | 双端真砸，下跌趋势 |
| + | − | + | 永续短轧（如单日暴涨日），现货未跟 |
| − | + | − | 现货抢筹但永续不信，反转初期 |
| 任意 + 单日 absorption | — | — | 仅当**单日**阳线 + 永续 Δ 大负且现货 Δ 也负，才标 `#absorption` |

### 步骤 M5：写结论前的 3 个自检

1. **如果我的结论对，应该还能看到什么数据？** → 拉出来确认；不能确认就降级为"假说"
2. **现货端是否支持这个叙事？** → 如果只在永续端成立、现货反向，结论作废
3. **funding 是否兼容？** → 如果叙事说"卖方主导"但 funding 长期正向，必然要解释空头被挤的可能
